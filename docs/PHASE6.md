# Phase 6 — Recovery history, redo and bounded block data

## Recovery history UX

Open **Recovery history** from the preview review screen or run `/craftgpt history`. The server returns at most the newest 50 validated journal entries belonging to the current player. The payload contains only placement/build IDs, dimension, timestamps, progress, status, conflicts and whether protected block data exists; coordinates, block states and NBT never cross to the client.

Select an entry, then choose **Undo selected** or **Redo selected**. A second click is required to confirm the exact action. Recovery is still operator-gated on multiplayer and uses the same rate limits, loaded-chunk checks, batching and persistent progress state as Phase 5.

## Ordering and conflicts

Every selected recovery action is server-resolved by placement UUID. Before mutating an older entry, the server checks newer journals in newest-first order. If a newer placement is not fully undone and shares a coordinate in the same dimension, the older action is rejected. This prevents an old snapshot from silently cutting through a newer CraftGPT build.

Undo and redo remain idempotent:

- expected source state and data: apply the recorded replacement;
- already at the complete replacement state and data: no-op;
- any other state or block-entity data: preserve it as a conflict.

A fully undone placement is redoable. A conflicted undo remains available for both retry and explicit redo. Redo completes as `redone` or `redone_with_conflicts` and can be undone again.

## Bounded block-entity support

The local setting **Existing block entities** defaults to protected/off. When explicitly enabled, CraftGPT may replace an already existing block entity only after the server captures its complete metadata into the immutable before-snapshot. This supports later recovery of containers, signs and similar existing data without sending it to the model or client.

Safety constraints:

- target blocks generated by the model may not be block entities;
- the model and API protocol cannot provide NBT;
- command blocks, spawners, portals and other denylisted states remain forbidden;
- at most 128 block-entity snapshots per placement;
- at most 64 KiB per block entity and 2 MB total serialized NBT;
- NBT must parse canonically and instantiate a block entity valid for the recorded block state;
- any NBT change after journaling creates a conflict instead of being overwritten.

The journal format remains schema-compatible with Phase 5: the new `beforeBlockEntityNbt` field is optional and omitted for ordinary changes, so existing `0.5.0` journals keep their original content hash.

## Remaining boundary

Phase 6 has automated protocol, storage, history-ordering, conflict and lifecycle tests. It does not yet include a live Minecraft GameTest that opens an inventory, performs a full NBT placement/undo/redo round-trip and simulates a server crash. Use a world backup for initial manual validation.
